# 05. コンテンツパイプライン（素材 → 問題）

素材を集め、**20 プロファイルすべてでエンコードして正解を確定**し、難易度を付け、配布アセットを作るまで。
**MVP は手動収集**、Phase 3 で自動化する。生成物の構造は [03](./03-data-model.md)。

---

## 1. 原則

1. **正解は実測でしか決めない。** パイプラインが実際にエンコードしてバイト数を比較する。
2. **再現可能にする。** 同じ素材＋同じプロファイル＋同じツール版 → 同じ結果。
   ツール版を記録し、変わったら**問題を作り直す**（[03](./03-data-model.md) §2）。
3. **冪等**。何度流しても同じ成果物。素材の内容ハッシュを ID の種にする。
   ⚠ **例外は回答用アセットのキー**（乱数なので入力からは決まらない）。
   **DB を正として再利用**することで冪等性を保つ（§2）。
4. **ライセンスを持ち回る。** 出典・作者・ライセンスが取れない素材は**採用しない**。
5. ⚠ **リサイズしない。** 縮小は PNG を大きく不利にする（[measurements](./_grilling/measurements.md) §5）。
   寸法を変えるなら「意図した加工」として `derivation` に記録する。

## 2. 手動フェーズ（MVP）

```
assets/source/<name>.<ext>      # 素材（原本）
assets/source/<name>.meta.json  # 出典・作者・ライセンス・カテゴリ・タグ（手書き）
        │  pnpm quiz:build
        ▼
build/questions.json                    # 問題 + 20 プロファイル分の実測値 + アセットのキー対応
build/assets/display/<hash>.webp        # 出題時に公開。キーは内容ハッシュ由来でよい
build/assets/encoded/<random>.png|.jpg  # 回答後のみ。🔒 キーは暗号学的乱数
        │  pnpm quiz:upload
        ▼
Cloudflare R2
```

🔒 **`display` と `encoded` を同じ階層に置かない。** 両者のキーが互いに導出できると、
display の URL を得た時点で回答用アセットのパスが推測でき、**回答前に HEAD で答えが取れる**
（[04](./04-session-and-integrity.md) §3.4）。

- `encoded` のキーは**問題 ID・プロファイル ID・display のキーのいずれからも導出できない乱数**にし、
  対応は DB（`question_encoded_asset`）だけが持つ（[03](./03-data-model.md) §5.2）。
- ⚠ **内容ハッシュも使えない。** 出題画像（可逆 WebP）からピクセルは復元できるので、
  同じ手順で PNG を作ればハッシュを計算でき、キーを言い当てられる。

### キーの発行と再利用（冪等性）

🔒 **`question_encoded_asset`（DB）がキーの唯一の正。** 生成物側のキーは常にその写しであり、
**DB に行を作らずにキーを発行してはいけない。**

**手順を「DB 先行」に固定する:**

| # | 段階 | 内容 |
|---|---|---|
| 1 | 照合 | `(question_id, profile_id, kind)` で既存行を引く。あればその `object_key` を使う |
| 2 | 予約 | 無ければ**先に DB へ行を作って** `object_key`（乱数）を確定する。この時点で `bytes` / `sha256` / `uploaded_at` は null |
| 3 | 生成 | 予約したキーで成果物を書き出し、`bytes` / `sha256` を DB へ書き戻す |
| 4 | 同期 | `pnpm quiz:upload` が**成果物のキーと DB の `object_key` を全件照合**し、**完全一致するものだけ**アップロードする。不一致、または DB に行が無いキーが 1 つでもあれば**エラーで停止**する |
| 5 | 記録 | アップロード成功後に `uploaded_at` を埋める |

- 🔒 **「upload 時に DB へ接続できること」を条件にしない。** 接続できても、その成果物が
  DB のキーで作られた保証にはならない。**キーの全件一致を前提条件にする**ことで、
  DB 無しで作られた成果物は必ず弾かれる。
- この順序なら、途中で失敗して残る不整合は「**DB に行があるが R2 に無い**」だけで、
  `uploaded_at IS NULL` で検出でき、再実行で解決する。
  逆向き（R2 にあるが DB に無い）は孤児であり、掃除コマンドが消す。
- ⚠ **`questions.json` を再利用元にしてはいけない。** これはコミットしない生成物なので（§2）、
  クリーンな CI・別端末・作業ディレクトリ再作成後のビルドでは存在せず、キーが振り直される。
- 孤児の掃除: R2 のオブジェクト一覧と `question_encoded_asset` を突き合わせ、
  参照されないキーを削除するコマンドを用意する。
- 💡 代替案として `HMAC(secret, question_id + profile_id + kind)` による安定導出も検討したが、
  **鍵が漏れると全問題のパスが導出できる**（乱数 + DB なら DB が漏れない限り安全）うえ、
  鍵のローテーションが全アセットの再アップロードを意味するため**採らない**。

- `pnpm quiz:build` が全工程を実行する。手で成果物を置くことはしない。
- 生成物は**リポジトリにコミットしない**（`.gitignore` 済み）。R2 が正。

## 3. 処理ステップ

| # | 段階 | 内容 |
|---|---|---|
| 1 | **取り込み** | 素材 + メタを読む。内容ハッシュを計算 |
| 2 | **適格判定** | アニメ / 極端に小さい / 重複ハッシュ → **除外**。ノイズ判定（§3.1）は**警告**（[01](./01-quiz-domain.md) §1） |
| 3 | **正規化** | sRGB・8bit・メタデータ除去・**背景合成（flatten）してからアルファ除去**。**リサイズしない** |
| 4 | **色数カウント** | 256 以下かを判定（可逆パレット化の可否に効く。`question.color_count`） |
| 5 | **エンコード** | **20 プロファイルすべて**で PNG / JPEG を生成し、バイト数を実測 |
| 6 | **判定** | プロファイルごとに `answer` = 小さいほう。同点は除外。`log2_ratio` を算出 |
| 7 | **静的難易度** | `\|log2_ratio\|` から算出。カテゴリ/タグと答えの**逆行**で加点 |
| 8 | **表示用アセット** | 可逆 WebP を 1 つ生成（[04](./04-session-and-integrity.md) §3） |
| 9 | **解説生成** | タグ + 比率から一行解説。手書きがあれば優先 |
| 10 | **出力** | `questions.json` / DB へ upsert。`status` は既定 `draft` |
| 11 | **レビュー** | 人が見て `published` にする。特に合成問題は見た目の破綻を確認 |
| 12 | **偏りの再計算** | `encode_profile.png_win_rate` をプール全体から再計算（[06](./06-ranking.md) §1） |

### 3.1 ノイズ判定（AI 生成画像の検出）

**AI 生成画像は、絵柄が平坦でも画素レベルにゆらぎを持ち、PNG が極端に不利になる**
（[measurements](./_grilling/measurements.md) §6）。見た目のカテゴリからは予想できないので、
**素材を機械的に測って印を付ける**。

| 指標 | 測り方 |
|---|---|
| `color_count` | 相異なる RGB の個数（ステップ 4 で計算済みのものを使う） |
| `flat_ratio` | **隣接ペアのうち一致するペアの割合**（定義は下記）。**空間的相関の直接の指標** |

#### `flat_ratio` の定義

**画素ではなく「有向隣接ペア」を数える。** 幅 `w` × 高さ `h` の画像について:

```
分母 = h*(w-1) + (h-1)*w      # 右方向のペア + 下方向のペア。境界は端から出るペアを作らないだけ
分子 = そのうち RGB 全チャンネルが完全一致するペアの数
flat_ratio = 分子 / 分母
```

- **対象は正規化後（ステップ 3 の後）の画像**。背景合成とアルファ除去が済んだ RGB で測る。
  原本の透明画素を含めると背景色に依存して値が動く。
- **右と下は別々のペアとして数える**（「両方向とも一致した画素」ではない）。
  片方向だけで数えると縦縞・横縞の扱いが非対称になる。
- **境界画素を分母から除くのではなく、境界から出るペアを作らないだけ**。
  したがって `w = 1` かつ `h = 1` のときのみ分母が 0 になるが、その寸法は適格判定（ステップ 2）で除外済み。
- 完全な単色画像なら `1.0`、隣接画素が毎回異なるノイズなら `0.0` に近づく。

- **判定**: `category` / `tags` が平坦系（`flat` / `illustration` / `pixel-art` / `ui`）なのに
  `color_count > 256` **かつ** `flat_ratio` が低い → **`noisy_flat` の警告**を出す。
- 🔒 **警告であって除外ではない。** これは「使えない素材」ではなく
  **「平坦に見えるのに PNG が効かない」＝ 直感を裏切る良問の候補**である
  （[01](./01-quiz-domain.md) §4.1 の「直感との逆行」に加点する）。
- **除外するのは人の判断**（ステップ 11）。判定結果は `question.derivation` に残し、
  正解画面の一行解説（ステップ 9）でも「AI 生成画像は平坦に見えてもノイズを持つ」と説明できるようにする。
- ⚠ **閾値は素材が増えたら見直す。** 現時点の手持ち 22 点では
  「AI 生成 18 点が全件 JPEG 勝ち」という極端な分布なので、**閾値のチューニングは早すぎる**。
  まずは指標を記録することを優先し、値は `flat_ratio < 0.5` を暫定とする。

### ⚠ エンコード実装の注意（実測で踏んだもの）

```ts
// PNG: effort を必ず明示する。省くと 4 倍のサイズになる
const png = await sharp(norm).png({ compressionLevel: 9, effort: 10 }).toBuffer()
// 可逆パレット化は oxipng が担う。sharp の palette:true は非可逆量子化なので使わない
const optimized = await oxipng(png, { level: 4 })
// JPEG
const jpeg = await sharp(norm)
  .jpeg({ quality, chromaSubsampling, progressive: true, mozjpeg: true }).toBuffer()
```

- `palette: false` を明示すると `effort` 指定が無視される（→ [measurements](./_grilling/measurements.md) §1）。
- ツール版（sharp / libvips / oxipng / mozjpeg）を `encode_profile.tool_versions` に記録する。

## 4. 「際どい問題」の合成（意図的な意地悪）

[01](./01-quiz-domain.md) §5 のネタを**パラメータ探索**で自動化する。

- 目的関数: **標準プロファイルでの** `|log2(png_bytes / jpeg_bytes)|` を 0 に近づける。
- 操作と探索パラメータ:

| 操作 | パラメータ | 効き方（実測） |
|---|---|---|
| ノイズ付与 | 振幅・粒度 | PNG を増やす。**振幅で連続的に動かせるので拮抗点を作りやすい** |
| **減色（ディザなし）** | 色数 | PNG を減らす。**16 色まで落として初めて効く**（下記） |
| ぼかし | 半径 | JPEG を減らす（強い） |
| ⚠ リサイズ | — | **使わない**。PNG が不利になりすぎる |

#### 🔑 減色は 16 色まで落とす。256 色では効かない

| 素材（AI 生成） | そのまま | 256 色 | **16 色** |
|---|---|---|---|
| 山のグラデーション | `log2 r` 3.54 | **3.55（変わらない）** | **0.11（超拮抗）** |
| イラスト調の街 | `log2 r` 1.11 | — | **-0.75（PNG 勝ちに反転）** |

- **理由**: PNG の圧縮を効かせているのは色数ではなく**隣接画素が同じ値であること**。
  256 色にパレット化しても、隣り合う画素が別のインデックスに散っていれば DEFLATE は伸びない。
  16 色まで落とすとゆらぎが同じ値へ丸められ、初めて圧縮が効く
  （[measurements](./_grilling/measurements.md) §6.1）。
- → **探索は「色数」を 256 から線形に下げても無駄**。**16 前後を起点**にし、
  2 / 4 / 8 / 16 / 32 / 64 のように**対数的に刻む**。
- ⚠ **ディザは使わない。** ディザは隣接画素をわざと散らすので、狙っている効果を打ち消す。
- ⚠ 16 色は**見た目が変わりやすい**。写真ではポスタリゼーションが目に見えるため、
  「明らかに減色されている」＝手がかりになる。**平坦寄りの絵柄に限って使い**、
  ステップ 11 の人手レビューで弾く。

- 単調性のある操作は**二分探索**で拮抗点を出せる。1 素材から複数の難易度の問題が作れる。
- ⚠ **見た目が壊れた画像は問題にしない**。ノイズを載せすぎた画像は「明らかに汚い」＝手がかりになる。
  振幅の上限を決め、ステップ 11 の人手レビューで弾く。
- 合成問題は `is_synthetic` / `derivation` に**加工内容を記録し、正解画面で開示**する
  （「元画像にノイズを載せています」まで見せて初めて教材になる）。

## 5. 自動収集（Phase 3）

### 素材ソース候補（要ライセンス確認）

| ソース | 性質 | ライセンス上の注意 |
|---|---|---|
| Wikimedia Commons | 実写・図版・イラストが混在。API あり | CC BY / CC BY-SA / PD が混在。**作者クレジット必須のものが多い** |
| Openverse | 横断検索 API。CC のみ | 出典元ごとに条件が違う |
| Unsplash / Pexels | 高品質な実写 | 各サービス独自ライセンス。API 利用規約と帰属表示の条件を確認 |
| 画像圧縮の評価用データセット（Kodak / DIV2K / CLIC 等） | 実写のバリエーションが体系的 | **研究用途限定のものがある。要確認** |
| パブリックドメインのイラスト・図版アーカイブ | イラスト側の厚みが出る | PD 表記の確認 |

- ⚠ **イラスト側の素材が集めにくい**のが構造的な弱点。合成（§4）と、
  自作スクリーンショット・ピクセルアート生成で補う。
- ⚠ **既に JPEG で配布されている素材**を元にすると、JPEG アーティファクトを含んだ状態から
  再エンコードすることになり、JPEG 側にわずかに有利に働く。可能なら可逆形式の原本を選ぶ。
- 収集は「取得 → 適格判定 → §3 のステップ 3 以降」に流し込むだけ。**取得層だけを差し替え可能にする**。

### 蓄積の運用

- 自動生成された問題は `draft` に入り、**人手レビューを経て `published`** にする。
- 出典・ライセンス表記のページを自動生成する（クレジット義務の履行）。

## 6. 検査（CI）

- `questions.json` の各行と実アセットの `bytes` / `sha256` が一致すること。
- `answer` が `png_bytes` / `jpeg_bytes` と矛盾しないこと（**20 プロファイルすべて**）。
- `published` な問題の**正規化後の画像に透過が残っていない**こと
  （原本に透過があってもよいが、`flatten` されずに素通りしたものは弾く。§3 ステップ 3）。
- `display` が**可逆 WebP** であること（**PNG が紛れ込んでいないこと**。
  [04](./04-session-and-integrity.md) §3.1 の絶対条件）。
- **PNG のサイズが異常に大きい問題がないこと**（`effort` 指定漏れの検出。目安: `bpp > 8`）。
- `published` な問題の**全アセットが `uploaded_at` を持つ**こと（未同期のまま公開しない）。
- **R2 に、DB から参照されないオブジェクトが無い**こと（孤児の検出）。
- `encode_profile.png_win_rate` が実際のプール分布と一致すること。
