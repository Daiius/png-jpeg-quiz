# PRD: PNG / JPEG どっちが小さい？クイズ

> **状態: Phase 0 完了（主要仕様は確定）**。決定の根拠と経緯は [`_grilling/decisions.md`](./_grilling/decisions.md)、
> 実測データは [`_grilling/measurements.md`](./_grilling/measurements.md)。

## 目的

フロントエンドの現場で繰り返し起きる「この画像は PNG と JPEG どっちで出すべき？」という判断を、
**2 択クイズ**に切り出して身体感覚として鍛える Web アプリ。**社外公開の一般向け。**

論点を割り切って、出題は次の一問に固定する:

> **この画像を、指定されたオプションで PNG と JPEG にエンコードしたとき、配布サイズが小さいのはどちらか。**

「劣化の度合い」「透過の要否」「表示品質」といった実務上の他の判断軸は、**あえて出題対象から外す**
（→ [01](./01-quiz-domain.md) §1）。ただし「サイズだけで決めると危ない」ことは解説で必ず伝える。

## 体験の骨子

- **開いた瞬間に 1 問目が出ている。** 開始ボタンも条件選択も挟まない（→ [06](./06-ranking.md) §2.1）。
- **1 セッション 30 問**。易しい問題から段階的に難しくなる。
- **エンコード条件は 20 プロファイルから選べる**（JPEG 品質 5 × サブサンプリング 2 × PNG 最適化の有無 2）。
  「オプションで変わるでしょ」という当然の疑問に、**実際に変えて確かめられる**ことで答える。
  既定は標準条件で、変えたい人だけが出題画面のダイアログから選び直す。
- 回答すると即座に**正解 ＋ 実測バイト数 ＋ PNG/JPEG 両方の実物**を提示する。
  開発者ツールで自分でも確かめられる（→ [04](./04-session-and-integrity.md) §4）。
- 得点は**サプライザル方式**。偏った条件を選ぶとハイリスク・ハイリターンになり、
  条件が違っても**1 本のランキング**で比較できる（→ [06](./06-ranking.md) §1）。

## 設計の柱

1. **正解はサーバだけが持つ。採点もサーバが行う。** クライアントは表示のみ。
2. **正解は事前に実測して確定しておく。** 出題時にエンコードしない（再現性・速度・エンコーダ版の固定）。
3. **エンコード条件はサイトに明示する。** 条件が変われば答えも変わる。条件は問題データに埋め込む。
4. 🔒 **答えの方向を示す情報を、回答前に一切出さない。** 配布バイト数だけでなく、
   **得点の重みも漏洩経路になる**（→ [04](./04-session-and-integrity.md) §3.5）。
5. **問題構成・競技基準は後から差し替えられるようにする。** 遊んでみて思いついたルールを足せるよう、
   `quiz-core` にモードを抽象として持たせる（→ [02](./02-architecture.md) §4-1）。
