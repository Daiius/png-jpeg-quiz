# 決定ログ（grill セッション: 2026-08-13）

> 仕様策定の経緯と根拠。**確定事項は PRD 本文へ昇格済み**で、ここは「なぜそう決めたか」を残す。
> 実測の生データは [`measurements.md`](./measurements.md)。

## 1. 出発点（ヒアリング前の与件）

フロントエンドチームで「PNG と JPEG の使い分け」が話題になった。実際の議論では画像サイズ以外に
劣化の度合いなど様々な観点が出たが、**今回は「配布サイズがどちらが小さいか」の 2 択に割り切る**。

- 難易度を少しずつ上げながら出題する。
- ゲームセッションの保持とサーバ側への記録、ランキング・連勝の記録を、
  **最低限の対タンパ性を持ちつつシンプルに**実装したい。
- エンコードオプションで結果が変わるので、**標準的なオプションをサイトに明示**する。
  際どい画像をあえて生成して意地悪な問題にすることも考えている。
  **正解は事前に実際にエンコードして記録**しておく。
- **正解表示時には PNG / JPEG 両方を表示**し、開発者ツールで実際に比較できるようにする。
- 問題素材は一旦手動で集める。最終的にはフリー素材集から自動生成して蓄積したい。
- アーキテクチャは Next.js 版と Vite + Hono 版の両方を考えたい。

### 2.2 標準エンコード条件（Q3）

| # | 決定 |
|---|---|
| **Q3-a** | **可逆パレット化を許す**（色数 ≤256 なら PNG-8）。減色（pngquant 等の非可逆量子化）は**しない** |
| **Q3-b** | **JPEG: q95 / 4:4:4 / progressive / mozjpeg**（2026-08-13 に q80 / 4:2:0 から変更） |
| **Q3-c** | **PNG: sharp（`effort` 明示）→ oxipng `-o4`** |

- **PNG・JPEG の両方を最高品質側に振った条件**にした。PNG は可逆なので画質の軸が無く、
  `oxipng -o4` は画質を落とさずサイズだけを詰めるため、これが PNG 側の最高設定にあたる。
- 校正母集団の取り方を 6 通り変えて測り、**5 通りで 4:4:4 の高品質側が選ばれた**
  （[measurements](./measurements.md) §7）。「出荷しそうな構成」16 点では PNG 勝率ちょうど 50%。
- ⚠ **旧決定の根拠は成立していなかった。** 「q80 の PNG 勝率 48% が最も 50:50 に近い」は
  27 素材の実測に基づいていたが、その 27 素材は合成物に偏っており（3 点が無効・1 点が重複・
  6 点は平坦に作ったもの）、**q80 を選ぶ母集団はその標本だけだった**（[measurements](./measurements.md) §6.3）。
- **Q3-a は oxipng を通して初めて実現される**。sharp の `palette:true` は非可逆量子化を伴うので使えない。
  可逆な color type reduction をやるのは oxipng（[measurements](./measurements.md) §2）。
- ⚠ **sharp の `png()` は `effort` を明示しないと 4 倍のサイズになる**（[measurements](./measurements.md) §1）。
- ⚠ **リサイズは PNG を大きく不利にする**。長辺 512/256 に縮小すると 27 件すべて JPEG 勝ちになった
  （[measurements](./measurements.md) §5）。**素材は原寸で扱う。**

### 2.3 対タンパ（Q7）

| # | 決定 |
|---|---|
| **Q7** | 出題画像は **可逆 WebP をそのまま配信**（パディングなし）。**PNG の直配信は禁止** |

- 実測: WebP のバイト数から答えを推測する戦略の的中率は 89%。ただし**外れた 3 件はいずれも拮抗問題**
  ——**易問は取られるが難問では漏れない**ので、パディングのコストに見合わないと判断
  （[measurements](./measurements.md) §4）。
- PNG を直に配ると `png_bytes` がそのまま見えるため、これだけは不可。
- ⚠ **パディングは剥がせる**（末尾チャンクを削れば元サイズが復元する）。将来パディングを入れる場合も
  「PNG にパディング」は無意味。**原理的に情報ゼロにできるのは非圧縮ラスタだけ**。

> 🔑 **レビューで判明した抜け穴（PR #1）**: 「回答前に `png`/`jpeg` の URL を渡さない」と書きながら、
> パイプラインの出力を `assets/<hash>/display.webp` と `assets/<hash>/<profile>/image.png` という
> **同じ階層**に置いていた。display の URL を得た時点で回答用アセットのパスが組み立てられ、
> HEAD リクエストで答えが取れる。**URL を渡さないことと、パスが推測できないことは別**。
> さらに**内容ハッシュをキーにするのも不可**——出題画像は可逆 WebP なのでピクセルを完全に復元でき、
> 同じ手順で PNG を作ればハッシュを計算できる。→ **キーは暗号学的乱数**にし、対応は DB だけが持つ
> （[04](../04-session-and-integrity.md) §3.4、[03](../03-data-model.md) §5.2）。

### 2.4 ゲームデザイン（Q4 / Q6 / Q14）

| # | 決定 |
|---|---|
| **Q4** | **20 プロファイル**（JPEG 品質 5 × サブサンプリング 2 × PNG 最適化の有無 2）を事前計算し、**ユーザーが選べる** |
| **Q6** | **fixed-n = 30 問**。難易度カーブに沿って段階的に難しくする |
| **Q14** | **サプライザル得点 `-log2(p)`**（`p` は**プロファイル単位**の答えの出現率）× **静的難易度重み**。条件が違っても 1 本のランキングに混ぜる |

議論の経緯（重要）:

1. まず「サプライザル正規化すれば条件選択と単一ランキングが両立する」と提案した。
2. → **「10 問しかないのに得点が減るオプションを選ぶ理由がない」と指摘され、これは正しかった**。
   サプライザルは不公平を消すが、**選ぶ動機まで消す**。
3. → さらに掘ると、**二択 × 10 問ではそもそも実力差が出ない**ことが分かった。
   実力 80% の人が 10 問全問正解する確率は 10.7%。100 人遊べば 10 人が満点でランキングが機能しない。
4. → **30 問に増やすことで両方が解決した**。満点確率は 0.12% に落ち、かつ
   **「偏った条件を選ぶと 1 問あたりの得点減が 30 問分積み上がる」トレードオフが成立**する。
   偏らせても、その条件で「当てにくい側」を見抜ければ高得点——という設計になる。

> 🔑 **教訓**: 「何を競わせたいか」を決める前にスコアリングを設計していた。順序が逆だった。

### 2.5 🔒 得点式そのものがサイドチャネルになる

得点式を決めるうえで**最も重要な制約**。[04](../04-session-and-integrity.md) §3.5 に脅威 T7 として記載。

- 一度「`p` を**実測正答率**にすれば、みんなが間違える問題ほど高得点になり、難易度推定と
  得点式が一本化されて美しい」と提案した。**これは誤りで、指摘を受けて撤回した。**
- **理由**: 二択なので「みんなが間違えている」＝「**直感と逆が正解**」が一意に決まる。
  得点の重みが答えの方向を指してしまう。
- 判断基準は「**その情報が対称か非対称か**」:

  | 情報 | 対称性 | 得点に使ってよいか |
  |---|---|---|
  | プロファイル全体の答えの偏り | 個別問題について何も語らない | ✅ 使う |
  | 静的難易度（サイズ比の拮抗度） | 「拮抗」と分かってもどちらが勝つかは決まらない＝**対称** | ✅ 使う（ただし**数値は回答前に見せない**） |
  | **実測正答率** | 「直感と逆」まで決まる＝**非対称** | ❌ **得点に使わない** |

- **帰結**: 実測正答率は「運営の分析」と「回答後の表示」に限定する。
  🔒 **問題別の正答率を、回答前に到達できる場所（統計ページ等）に置かない。**
- ⚠ 難易度カーブに沿って出題する時点で「後半ほど難しい」は既に開示されている。
  完全に潰すにはランダム出題にするしかなく体験を損なうため、**粗い開示（順序）は許容し、数値は伏せる**。

**結果としての得点式**:

```
得点 = Σ [ 正解 × 静的難易度重み × ( -log2( そのプロファイルでのその答えの出現率 ) ) ]
```

この形により、**偏った条件はハイリスク・ハイリターン**になる。q60（PNG 勝ち 30%）で JPEG を当てても
`-log2(0.7)=0.51` 点だが、PNG を見抜けば `-log2(0.3)=1.74` 点。期待値はエントロピーなので
標準条件（50:50）が最大だが、上振れの余地が残る。**公平性を壊さずに、偏った条件を選ぶ動機が生まれる。**

### 2.6 分析（ゲーム結果の処理）

- **MVP: ログ完備 + 結果画面の統計**。運営分析は SQL / スクリプトで行い、
  見たい指標が固まってから画面化する。
- `session_question` に全回答（出題時刻・回答・正誤・経過時間・プロファイル）を残すので、
  **集計は後から何でもできる**。MVP で作り込むべきはログの完全性であって可視化ではない。
- 結果画面に出すもの: パーセンタイル / 得点分布 / **問題別正答率（回答後のみ）**。

### 2.7 拡張性（開発中に効かせる方針）

**違う問題構成・競技基準を後から入れる前提で作る。** 遊んでみて思いついたものを足せるように、
`quiz-core` に**モードを抽象として持たせる**（問題数 / 条件選択の可否 / スコアリング関数 / 終了条件）。

- 後から足す候補: **endless（連勝）**、**確信度つき予測（log score）**、デイリーの変則ルール。
- 確信度モードは検討したが MVP からは外した。「PNG だと思う・確信度 70%」と宣言して
  `log2(q)+1` で採点する方式。**二択の情報量不足を根本から解く**が、UI が一段複雑になる。
  サプライザルと同じ proper scoring rule なので、**スコアリング関数の差し替えだけで載る**。

## 3. まだ決めていないこと

- **問題プールの目標規模**。30 問セッションを回すには、リピートを考えて 150〜300 問は要る見込み。
  素材の集め方（[05](../05-content-pipeline.md) §5）と合わせて Phase 1 の途中で見直す。
- **難易度カーブの具体的な刻み**（30 問をどう配分するか）。実プレイの正答率が出てから。
- **デイリーチャレンジの設計**。日替わりでプロファイルを振る案は有力だが、通常プレイで条件を
  選べるようにしたため、差別化の意味が薄れた。Phase 2 で再検討。
- **教材性をどこまで持たせるか**（解説の厚み、学習の進捗表示）。
- **1 プレイの体感時間**。30 問 × 20 秒は最大 10 分。長すぎないかは遊んでから。
