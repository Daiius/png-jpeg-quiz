# 06. 得点・ランキング・分析

得点式と記録の設計。データ構造は [03](./03-data-model.md)、漏洩の制約は [04](./04-session-and-integrity.md) §3.5。
設計の経緯は [`_grilling/decisions.md`](./_grilling/decisions.md) §2.4〜2.6。

---

## 1. 得点式（サプライザル方式）

```
得点 = Σ [ 正解 × 静的難易度重み(question) × ( -log2( p_profile(その問題の答え) ) ) ]
```

- **`p_profile(answer)`** = そのプロファイルの**問題プール全体**で、その答えが占める割合。
  `encode_profile.png_win_rate` から求める（[03](./03-data-model.md) §2）。
- **静的難易度重み** = `|log2_ratio|` から算出した値（拮抗しているほど大きい）。
  🔒 **数値は回答前に見せない**（[04](./04-session-and-integrity.md) §3.5）。
- 不正解は 0 点。⚠ **時間切れは無い**（制限時間を廃止した。[04](./04-session-and-integrity.md) §5.1）。
- **色数ヒントを開示した問題は ×0.5**（→ §7）。

### なぜこの形か

**条件選択とランキングの両立**が目的。プロファイルを自由に選べるので、
「有利な条件を選んで稼ぐ」抜け道を塞ぎつつ、**選ぶ動機は残す**必要があった。

- q60（PNG 勝ち 30%）で JPEG を当てても `-log2(0.7) = 0.51` 点。
- しかし **PNG を見抜けば `-log2(0.3) = 1.74` 点**。
- 期待値はエントロピー `H(p)` なので **50:50 の標準条件が最大**。偏った条件は期待値が低い代わりに**分散が大きい**。

→ **偏った条件はハイリスク・ハイリターン**。30 問あるので分散は均され、
平均的には標準条件が有利。それでも「自分は少数派を見抜ける」人には上振れの余地がある。
**条件が違っても 1 本のランキングに混ぜられる。**

### 🔒 実測正答率を得点に使わない

一度「`p` を実測正答率にすれば難易度推定と得点式が一本化されて美しい」と設計したが、**誤りだった**。
二択では「みんなが間違える」＝「**直感と逆が正解**」が一意に決まり、得点の重みが答えの方向を指す。

- **使ってよいのは対称な情報だけ**（プロファイル全体の偏り / サイズ比の拮抗度）。
- 実測正答率は**非対称**なので、運営分析と回答後の表示に限定する。
- 詳細は [04](./04-session-and-integrity.md) §3.5。

### 検討したが採らなかったもの

- **時間ボーナス**: 二択なので「当てずっぽうで即答」が最適戦略になりかねない。入れない。
  経過時間はログに残すだけ（[03](./03-data-model.md) §7）。
- **確信度つき採点（log score）**: 二択の情報量不足を根本から解く優れた方式だが、UI が複雑。
  同じ proper scoring rule なので、**モードの差し替えだけで後から載る**（§2）。

## 2. モードとプロファイル

| | MVP | 内容 |
|---|---|---|
| **`standard-30`** | ✅ | **30 問固定**。難易度カーブに沿って出題。プロファイル選択可 |
| `endless` | Phase 2 | 不正解まで。記録は連勝数。**問題プールの深さが要る** |
| `confidence` | Phase 2 | 確信度つき予測。`log2(q)+1` で採点 |

- モードは `quiz-core` の抽象（[02](./02-architecture.md) §4-1）。**遊んでから思いついた基準を足せる**。
- **プロファイルはセッション開始時に固定**（[04](./04-session-and-integrity.md) §2）。

### 2.1 開始フロー: 既定条件で即座に始める

🔑 **`/` を開いた時点で 1 問目が出ている。** 開始ボタンも条件選択も挟まない。

**何をするサイトかは、設定画面の説明文ではなく問題そのもので伝える。** 20 プロファイルは
「オプションで変わる」ことの実演として重要だが（[README](./README.md)）、**入口に置く必然性は無い**
——面白い条件は実質ほぼ 1 つで、選択を最初に出しても大半の人は既定のまま始める。

- 既定はサーバが決める。**プロファイルは標準条件**（遊べない条件なら最初の遊べる条件）、
  **モードはプールの大きさ**で `standard-30` / `practice` を選ぶ（§2）。
  → `POST /api/session` は **body 省略で「おまかせ開始」**（[02](./02-architecture.md) §4-2）。
- **条件の変更は出題画面のダイアログ**から行う。⚠ プロファイルはセッション開始時に固定される
  （[04](./04-session-and-integrity.md) §2）ので、**変更＝新しいセッションの開始**であって途中変更ではない。
  進行中のセッションを捨てることをダイアログに明示する。
- **説明は画面下部に置く**（このクイズについて / **適用中の条件の中身** / 正解はサーバが持つこと /
  条件詳細・クレジットへのリンク）。出題画面の下にスクロールで到達する。
  ⚠ 下部に出す条件は**表示のみ**にし、選ぶ UI はダイアログへ一本化する。
  同じ操作が 2 箇所にあると、どちらがセッションを作り直すのか分からなくなる。
- 🔒 URL は `/?session=<id>` に差し替える（`history.replaceState`）。リロードで同じセッションに戻れること。
  **セッション ID は URL・`secret` は HttpOnly Cookie** の分離は変えない（[04](./04-session-and-integrity.md) §2）。
  - 「戻れる」には**得点・進行・直前の正解画面**を含む（状態 API `GET /api/session/:id`。
    [02](./02-architecture.md) §4-2）。回答直後にリロードしても正解画面に戻れること——
    原則 5「検証できる状態にする」は、検証のためにリロードした人が損をしない形で初めて成立する。
    ⚠ **次問のプリフェッチ後は復元先が出題画面になる**（次問が配信済みのため）。その場合も
    出題画面の「前の問題の結果を見直す」導線から直前の開示に戻れること（導線は完走画面にも置く）。

#### 引き換えに受け入れたもの

- ⚠ **セッションは訪問ごとに作られる。** クローラの巡回でも `session` 行が増える。
  レート制限（[04](./04-session-and-integrity.md) §5.2）で受け止める前提。
- ⚠ **1 問目の `elapsed_ms` には説明を読む時間が乗る**（[03](./03-data-model.md) §7）。
  時間は得点に使っていないので害は分析ノイズに留まるが、**時間を競技基準にするモードを足すときは
  1 問目を特別扱いする**必要がある。
- ⚠ 「画像だけ先に見せて、最初のクリックでセッションを作る」形は**採らない**。
  `served_at` がクリック後になり、最短回答時間の下限（300ms）に自分で引っかかる
  （[04](./04-session-and-integrity.md) §5.2）。

### なぜ 30 問か

⚠ **二択 × 10 問では実力差が出ない。** 実力 80% の人が 10 問全問正解する確率は **10.7%** で、
100 人遊べば 10 人が満点になりランキングが機能しない。20 問で 1.2%、**30 問で 0.12%**。
加えて 30 問あることで、偏った条件を選んだときの得点減が積み上がり、§1 のトレードオフが成立する。

## 3. ランキング

- 掲載単位は `score_entry`（セッション確定時のスナップショット。[03](./03-data-model.md) §9）。
- ビュー: **全期間 / 今日**、および参考として最長連勝。
- **プロファイルが違っても同じランキング**（サプライザル正規化）。使った条件は表示する。
- 表示名は任意入力（[04](./04-session-and-integrity.md) §6）。未入力なら匿名として集計のみ。
- `flagged` は集計から外すが、本人の画面では通常どおり見える。

## 4. 結果画面の統計

プレイヤーに見せるもの。**問題を特定した正答率は、回答後にのみ出す**。

| 表示 | 内容 | 漏洩 |
|---|---|---|
| パーセンタイル | 「上位 23%」 | 問題を特定しないので安全 |
| 得点分布 | 全プレイのヒストグラム上に自分の位置 | 同上 |
| **問題別の正答率** | 「この問題は 78% が間違えています」 | **回答後なので安全**。⚠ 統計ページには出さない |
| 20 プロファイルの結果 | この画像は q60 では JPEG、q95 では PNG | 回答後なので安全 |

## 5. 共有（Phase 2）

- 結果ページ `/r/<session_id>`（read-only）と OGP 画像。Next.js の Server Components で生成する。
- 共有カードに載せるもの: モード・条件・スコア・正答率。
  🔒 **問題の正解は載せない**（未プレイの人へのネタバレ・漏洩になる）。

## 6. 分析（運営）

**MVP はログ完備 + SQL / スクリプト。** 可視化は見たい指標が固まってから作る
（[03](./03-data-model.md) §7 に全回答が残るので、集計は後から何でもできる）。

見たい指標:

| 指標 | 用途 |
|---|---|
| 問題別の正答率（プロファイル別） | **みんなが間違える問題の把握**。素材選定の質 |
| 静的難易度と実測正答率の**乖離** | 「拮抗していないのに全員間違える」＝ 直感と逆行する良問の発見 |
| プロファイル別のプレイ数・スコア分布 | 条件選択が機能しているかの検証 |
| 何問目で離脱するか | 30 問が長すぎないかの判断 |
| 回答時間の分布 | 1 プレイの体感時間の把握。**極端に長い回答が増えていないか**（T3 の兆候。[04](./04-session-and-integrity.md) §5.1 で受容済みだが、規模は見ておく） |

- ⚠ **実測正答率を難易度に反映するかは慎重に。** 反映すると難易度経由で答えの方向が漏れる
  （[04](./04-session-and-integrity.md) §3.5）。**現時点では反映しない**方針。
  「正答率が極端に低い問題を retire する / 出題頻度を下げる」といった**運営判断の材料**としてのみ使う。

## 7. ヒント（色数レンジ）

**減点と引き換えに、その画像の色数を 2 段階のレンジで開示する。**
答えの方向と相関する情報を回答前に出すので、**T7（[04](./04-session-and-integrity.md) §3.5）の
唯一の例外**にあたる。例外が成立する 4 条件は [04](./04-session-and-integrity.md) §3.6、
経緯と採らなかった案は [`_grilling/decisions.md`](./_grilling/decisions.md) §2.9。

### 7.1 何を出すか — 実数ではなく 2 段階

`question.color_count`（[03](./03-data-model.md) §3）を次の 2 段階に落として出す。境界は 256 のみ:

| 表示 | 含意 |
|---|---|
| **「256 色以下」** | 可逆パレット化が届く領域（[01](./01-quiz-domain.md) §3.1） |
| **「256 色超」** | パレット化は効かない。**平坦に見えてもノイズを疑う**領域 |

- **なぜ色数か**: 「見た目からは分からないが、観察眼を鍛えれば見積もれるようになる」画像の
  静的実測値だから。AI 生成の「単色ベタ塗り」に 769 色ある
  （[measurements](./_grilling/measurements.md) §6.1）——このギャップは本アプリが教えたい直感そのもので、
  **教材価値と漏洩が同じ一つの事実に同居する**。だから無償にせず、減点で対価づけする（§7.2）。
- **なぜ実数を出さないか**（3 つとも独立の理由）:
  1. **実数は問題の指紋になる。** レンジなら同値類が大きく、プール横断の照合・共有に使えない。
  2. **「16 色」は意地悪問題の自白になる。** 減色合成（[05](./05-content-pipeline.md) §4）は
     16 色前後を使うので、写真調の絵で実数 16 が出たら「人工的に拮抗させた問題」と特定できる。
     2 段階ならどちらも「256 色以下」に混ざり、罠が生きる。
  3. **実数の大小は誤学習を招く。** PNG を壊すのは色数ではなく空間的相関で、
     769 色も 20,295 色も同じように JPEG 勝ちに寄る（[measurements](./_grilling/measurements.md) §6.1）。
     教材として意味のある境界は「パレット化が効くか」の 256 だけ。
- **3 段階以上にもしない。** 16 の境界を露出させると 2 が崩れ、256 超側を細分しても
  3 の理由で答えとの相関はほぼ増えず、指紋性だけが増える。
- ⚠ **レンジでも、AI ノイズ系では答えをほぼ確定させる**（平坦に見えるのに「256 色超」）。
  **粒度で漏洩は消せない**——消える粒度まで潰すとヒントの価値も消える。
  漏洩は隠すのではなく、§7.2 で値付けする。
- 色数は `question` の属性で**プロファイル非依存**。oxipng 無しのプロファイルでは
  「パレット化が効く」の含意は弱まるが、レンジの定義も減点率も変えない
  （条件はプレイヤー自身が選んだ公開情報。[01](./01-quiz-domain.md) §3.2）。

### 7.2 減点 — 全問一律の定率 50%

```
awarded = 静的難易度重み × ( -log2 p ) × ( ヒント使用なら 0.5 )
```

- 🔒 **定率・全問一律。** 「その問題でのヒントの情報量」に応じて変えると、
  **減点率そのものが答えの方向を指す第二の漏洩経路**になる（T7 の再帰）。
- 0.5 で次の 3 つが同時に成り立つ（S = その問題の満額、q₀ / q₁ = ヒント無し / 有りの自分の正解率）:
  1. **「見て正解」（0.5 S）＞「見ずに不正解」（0）。** 対価を払って当てた人が、失敗より下にならない。
  2. **ヒント戦略の期待値の上限 ＝ 当てずっぽうの期待値。** ヒントが答えを確定させても
     EV は 1 × 0.5 S で、コイン投げの 0.5 × S と同じ。しかも分散は小さいので、
     **ヒントを使い倒してもランキング上位には届かない**（上位は上振れで決まる）。
  3. **損益分岐は q₁ × 0.5 > q₀。** q₁ ≤ 1 なので **q₀ < 0.5 の問題でしか引き合わない**
     ——自分の直感が五分を割る問題、つまり直感が裏切られる問題でだけヒントが立つ。教材の核心と一致する。
- ⚠ **0.5 より緩めると性質 2 が崩れる。** 例えば −30% では、確定に近いヒントの EV 0.7 S が
  当てずっぽうを超え、AI ノイズ系でのヒント連打が合理戦略になる。
  緩和はランキングの信頼性（[04](./04-session-and-integrity.md) §1 の守る対象①）と引き換えであることを
  知って行う。数値は暫定（→ [`_grilling/decisions.md`](./_grilling/decisions.md) §3）。
- ⚠ **連勝数は減点できない量**なので、連勝を競技基準にするモード（endless）にはヒントを載せない（§7.4）。
  `standard-30` 内の streak 表示はヒント使用を区別しない（対価は得点で払い済み。二重に罰しない）。

### 7.3 サーバの手順

- `POST /api/session/:id/hint`（[02](./02-architecture.md) §4-2）。
  🔒 **永続化が開示に先行する**: `session_question.hint_used_at`（[03](./03-data-model.md) §7）を
  書いてからレンジを返す。**開示した時点で減点が確定**し、以後の回答内容・正誤に関係しない。
- 冪等: 同じ問題への再要求は保存済みのレンジを返す（二重減点しない）。**回答済みの行への要求は拒否**。
- リロード復元（`GET /api/session/:id`）には**支払い済みの**ヒント（使用の有無とレンジ）を含めてよい。
- 使用回数の上限は設けない。減点が自己抑制であり、全問使用の期待値は §7.2 の性質 2 で抑えられている。
- **回答後は `color_count` の実数を開示する**（原則 5 の一部。[04](./04-session-and-integrity.md) §4）。

### 7.4 モードとの関係

- ヒントは**モード定義のオプション**（[02](./02-architecture.md) §4-1）:
  `standard-30` は減点 0.5 で許可、`practice` は減点なしで許可（ランキングに載らないため）。
  持たないモード（endless 等）は宣言しなければよい。全モード共通の機能にはしない
  （§7.2 の性質はサプライザル得点の上で成り立つもので、別の採点法に自動では移らない）。
- `quiz-core` は純関数のまま: レンジ化（`color_count` → 2 値）と、`score()` が
  コンテキストの「ヒント使用済み」を係数へ反映するだけ。DB・HTTP・UI は知らない。

### 7.5 UI

出題画面の情報欄（画像の下。sticky な 2 択ボタンとは離れた位置）に「ヒントを見る」の控えめな
ボタンを置き、**同じボタンの 2 度押し**で開示する。1 度目はボタンの下に警告文を出すだけで、
サーバへは何も送らない。2 度目で初めて開示を要求する——**誤タップ一発では開示されない 2 段階**を
ここで担保する。

- ⚠ **ボタンのラベルに減点を書かない**（2026-08-20 に確認ダイアログ方式から変更）。
  「ヒントを見る（減点なし）」の括弧書きは**「ヒントを見ても減点されない」と読める**。
  減点の話は 1 度目の押下で出す警告文に、モード（§7.4）ごとの文言で書く:

  | モード | 警告文 |
  |---|---|
  | 減点あり（`standard-30`） | 「ヒント（色数表示）を見ると得点が **−50%** になります。もう一度押すと表示します」 |
  | `practice` | 「練習モードなので減点はありません。もう一度押すと表示します」 |

- 🔒 **警告文の −50% はモード定義（§7.4 の `HintConfig`）から算出する。** UI 側に数値を書かない
  （減点率の二重定義を作らない。§7.2 を変えたら文面も自動で追随する）。
- **警告文は `aria-live` の live region に出す。** 読み上げ環境でも 1 度目の押下で警告が届く。
  live region は最初から DOM に置いておき、**中身だけ差し替える**（後から領域ごと差し込むと
  読み上げが起きない環境がある）。要求の失敗もこの領域に出す（エラーを警告より優先）。
- 開示後はレンジをバッジで表示し続け、回答ボタンの脇にも「ヒント使用中 −50%」を出す
  （減点を忘れたまま採点されて驚かせない）。開示の瞬間だけバッジへフォーカスを移す。
- **確認ダイアログは採らない。** 開示を止める効果は 2 度押しと変わらず、モーダルの開閉ぶんだけ
  30 問の流れを止める（「見る → 打つ」のリズム。[README](./README.md)）。
