# 01. 出題ドメイン（PNG / JPEG）

クイズそのものの定義、判定の根拠となる圧縮の性質、サイトに明示するエンコード条件、難易度の定義。
データ構造は [03](./03-data-model.md)、素材の作り方は [05](./05-content-pipeline.md)。
**本章の数値はすべて [`_grilling/measurements.md`](./_grilling/measurements.md) の実測に基づく。**

---

## 1. 出題の定義

**問い**: 表示されている画像を、§3 のプロファイルで PNG と JPEG にエンコードしたとき、
**ファイルサイズが小さいのはどちらか**。選択肢は `PNG` / `JPEG` の 2 択のみ。

- **正解＝実測値の比較**。事前にエンコードして記録した `png_bytes` / `jpeg_bytes` の大小で決める
  （→ [05](./05-content-pipeline.md)）。推定や理論では決めない。
- **出題対象は「サイズ」だけ**。劣化の許容度・透過の要否・用途は問わない。
  - 現場の判断はサイズだけでは決まらない。**この割り切りは意図的**であり、
    正解画面と About ページで明示する（→ §6）。
- **同点**（バイト数が完全一致）の問題は**採用しない**（[05](./05-content-pipeline.md) のフィルタで除外）。

### 透過を持つ画像は「背景に合成してから」出題する

**アルファチャンネルを持つ画像は除外しない。単色背景に合成（flatten）して不透明にしてから出題する。**

- **合成後は両形式とも同じ不透明画像をエンコードする**ので、比較の公平性は保たれる。
  除外していたのは「JPEG が透過を表現できない」ためであり、**透過を消してしまえば理由が消える**。
- 背景色は**素材ごとに `<name>.meta.json` の `preprocess.flatten` で指定**する（既定は `#ffffff`）。
  素材の見た目が壊れない色を人が選ぶ（例: 白線のイラストに白背景を敷かない）。
- 🔒 **合成後の画像が正解の根拠**。`png_bytes` / `jpeg_bytes` / `display` はすべて合成後から作る。
  合成前の原本を配ることはしない。
- 背景色は加工なので `derivation` に記録し、正解画面で開示する（→ [05](./05-content-pipeline.md) §3）。

> ⚠ **背景色は答えを動かす。** 白背景は平坦な面を増やすので PNG に有利、複雑な背景なら逆に働く。
> 恣意的に見えないよう、**特別な理由がなければ白**にし、変えたときは `derivation` に理由を書く。

### 出題対象外の画像

| 除外するもの | 理由 |
|---|---|
| アニメーション / 複数フレーム | 対象外 |
| 8bit/ch を超える深度・非 sRGB | 前処理で正規化するか除外（→ §3） |

> ⚠ 「透過が要るなら PNG（or WebP）」は現場では**サイズ以前の決定要因**。
> 合成して出題する以上クイズの問いには入らないが、解説では触れる。

## 2. なぜ二択が成立するのか（判定の根拠）

| | PNG | JPEG |
|---|---|---|
| 方式 | **可逆**。フィルタ（差分予測）＋ DEFLATE | **非可逆**。色空間変換＋クロマ間引き＋ DCT ＋量子化＋ハフマン |
| 得意 | 平坦な面、少色数、繰り返しパターン、シャープなエッジ | 自然画像、なだらかなグラデーション、ノイズを含む面 |
| 苦手 | **ノイズ・微細なテクスチャ**（可逆なので捨てられず、そのままビットになる） | **シャープなエッジ**（リンギング）、極端な少色（品質を上げると膨らむ） |

実測から言える典型（→ [measurements](./_grilling/measurements.md) §2）:

- **PNG が勝つ**: ピクセルアート（1,111 vs 5,596）、8 色 UI（4,414 vs 72,889）、
  フラットなイラスト（7,856 vs 16,011）、**フラット + 微細ノイズ**（17,409 vs 36,469）。
- **JPEG が勝つ**: 実写全般（383,968 vs 150,899）、グラデーション（12,458 vs 6,399）、
  **ぼかした写真**（169,915 vs 37,926）、グレースケール写真。
- ⚠ **アンチエイリアスの有無が効く。** 同じ UI 画像でも、アンチエイリアスが乗って色数が
  256 を超えると PNG が急に不利になる（65,467 vs 84,510 の僅差 → 8 色版なら 4,414 vs 72,889 の圧勝）。

## 3. エンコードプロファイル

**エンコードのオプション次第で答えは変わる。** そこで本アプリは条件を隠さず、
**20 プロファイルを事前計算してユーザーに選ばせる**（→ [06](./06-ranking.md) §2）。

### 3.1 標準プロファイル（`q95-444-oxi-v1`）

サイトの既定であり、**ランキングの基準となる条件**。
**PNG・JPEG の両方を最高品質側に振った条件**である。

> **プロファイル ID の命名は 20 個すべて同じ規則**にする: `q<品質>-<サブサンプリング>-<png最適化>-v<版>`。
> 標準だけ別名を持たせない（`std-v1` のようなエイリアスは作らない）。
> 「標準」であることは `encode_profile.is_standard` で表し、表示名は `published_label` で持つ
> （→ [03](./03-data-model.md) §2）。以降、本 PRD で「標準プロファイル」と書いたら `q95-444-oxi-v1` を指す。

| 項目 | 値 |
|---|---|
| **前処理** | sRGB へ変換 / ICC 除去 / 8bit/ch / メタデータ全除去 / **アルファは背景色に合成してから除去**（§1）/ **リサイズしない** |
| **PNG** | sharp（`compressionLevel: 9`, **`effort` を明示**）→ **oxipng `-o4`**。色数 ≤256 なら**可逆パレット化**（減色はしない） |
| **JPEG** | **quality 95** / **4:4:4**（クロマ間引きなし）/ progressive / **mozjpeg** |
| **比較** | ファイルのバイト数。転送時圧縮（gzip/br）は考慮しない |

**根拠**: 校正母集団の取り方を 6 通り変えて測り、**5 通りで 4:4:4 の高品質側が選ばれた**
（→ [measurements](./_grilling/measurements.md) §7）。「出荷しそうな構成」の 16 点では
**PNG 勝率ちょうど 50%**。

> 🔑 **PNG に「画質」の軸は無い。** 可逆なので画質は常に最高で、動かせるのは最適化の強さだけ。
> `oxi`（oxipng `-o4`）は**画質を落とさずサイズだけを詰める**ので、これが PNG 側の最高設定にあたる。
> つまり標準プロファイルは「両方を最高設定で書き出したとき、どちらが小さいか」を問う。

> ⚠ **旧標準 `q80-420-oxi-v1` からの変更（2026-08-13）。** 旧標準の根拠だった「27 素材で PNG 勝率 48%」は、
> **その 27 素材が合成物に偏っていた**ため成立していなかった（3 点が無効・1 点が重複・6 点は平坦に作ったもの。
> → [measurements](./_grilling/measurements.md) §6.3）。**q80 を選ぶ母集団は、q80 を決めた当の標本だけだった。**
> 切り替えに必要なのは `pnpm db:seed`（`is_standard` の付け替え）と `pnpm quiz:recalc` のみで、
> **アセットの作り直しは不要**（20 プロファイル分は既に事前計算されている）。

### 3.2 選択できる 20 プロファイル

| 軸 | 値 |
|---|---|
| JPEG 品質 | 60 / 75 / 80 / 90 / **95** |
| クロマサブサンプリング | 4:2:0 / **4:4:4** |
| PNG 最適化 | **oxipng -o4 あり** / なし（sharp のみ） |

**品質を上げるほど PNG が有利になる。** 現行の素材プール 22 点での実測:
q60-420 **0%** → q80-420 5% → q90-444 14% → **q95-444 27%**。
素材 1 点あたりで見ると、プロファイルを振るだけで `log2 比` が **1.6 前後動く**
（`commons-convex-cone`: q60-420 で +0.33 → q95-444 で −1.51）。

⚠ **PNG 最適化の強さは、ほとんど答えを動かさない。** `sharp effort:10` → `oxipng -o4` の
削減は合計 7.9%（**log2 で 0.118**）にすぎず、`-o4` → `-o6` はさらに 0.04% しか縮まない
（22 点中 14 点は 1 バイトも縮まなかった）。**プロファイル選択の 1.6 に対して 13 分の 1。**
ただし色数が十分少ない画像では oxipng の**可逆パレット化が階段状に効く**（8 色 UI で 3.7 倍、
ピクセルアートで 4.3 倍）ので、`oxi` の有無は少色素材でだけ答えを変える
（→ [measurements](./_grilling/measurements.md) §7）。

### 3.3 ⚠ 実装上の落とし穴（実測で踏んだもの）

- **`sharp.png()` は `effort` を明示しないと 4 倍のサイズになる。** `compressionLevel` はほとんど効かず、
  `palette: false` を明示すると `effort` 指定が無視される（→ [measurements](./_grilling/measurements.md) §1）。
- **可逆パレット化は oxipng が担う。** sharp の `palette: true` は非可逆量子化を伴うので**使わない**。
  8 色 UI が 16,273 → 4,414（3.7 倍）になるのは oxipng の color type reduction による。
- **リサイズは PNG を大きく不利にする。** 長辺 512/256 に縮小すると 27 件すべてが JPEG 勝ちになった。
  再サンプリングで中間色が生まれ色数が増えるため。**素材は原寸で扱う**
  （→ [measurements](./_grilling/measurements.md) §5）。
- **エンコーダのバージョンを記録する。** 版が変わればバイト数も変わり、拮抗問題では**正解が反転しうる**。

## 4. 難易度

### 4.1 難易度の軸

1. **サイズ比の近さ** — `r = png_bytes / jpeg_bytes` として `|log2 r|` が 0 に近いほど難しい。主軸。
2. **直感との逆行** — 見た目のカテゴリ（写真 / イラスト / スクショ）から素直に予想した答えと実測が食い違う。
3. **手がかりの乏しさ** — 低コントラスト・情報量が中庸で、どちらの得意領域にも寄らない。

### 4.2 難易度の決め方

- **静的難易度は 1 の実測から機械的に算出**する。2 は素材のタグ付けから加点する。
- 🔒 **実測正答率は静的難易度に混ぜない。得点にも使わない。**
  二択では「みんなが間違える」＝「直感と逆が正解」が一意に決まり、**答えの方向が漏れる**
  （→ [04](./04-session-and-integrity.md) §3.5）。実測正答率は運営分析と回答後の表示に限定する。

### 4.3 難易度カーブ

- 1 セッション **30 問**。易しい問題から段階的に難しくする。
- 同一セッション内で同じ問題を二度出さない。
- ⚠ カーブがある時点で「後半ほど難しい」は開示されている。これは許容するが、
  **難易度の数値そのものは回答前に見せない**（→ [04](./04-session-and-integrity.md) §3.5）。

## 5. 「意地悪な問題」の作り方

意図的に拮抗させた合成問題を混ぜる（生成手続きは [05](./05-content-pipeline.md) §4）。実測で効果を確認した順:

| ネタ | 効き方（実測） |
|---|---|
| フラットなイラストに**微細ノイズ**を乗せる | PNG 17,409 vs JPEG 36,469。**振幅で連続的に動かせる**ので拮抗点を作りやすい |
| 写真を**減色**する（16 色） | PNG 152,034 vs JPEG 158,850。**PNG 最適化の有無で答えが反転する**ほどの僅差 |
| **AI 生成画像を 16 色に減色**する | `log2 r` 3.54 → **0.11**、1.11 → **-0.75（PNG 勝ちに反転）**。⚠ **256 色では効かない**（→ [05](./05-content-pipeline.md) §4） |
| アニメ調のフラット塗り＋アンチエイリアス | PNG 14,073 vs JPEG 19,161。平坦面と斜めエッジの中間色が拮抗する |
| **強くぼかした**写真 | PNG 169,915 vs JPEG 37,926。高周波が消えて JPEG が極端に小さい。易問側の教材 |
| ⚠ リサイズで小さくする | **逆効果**。PNG が不利になりすぎる（§3.3） |

> 合成した画像も**出典と加工内容を記録**し、正解画面で開示する（→ [05](./05-content-pipeline.md) §4）。

## 6. 解説（正解画面で伝えること）

正解画面は「当たった/外れた」だけで終わらせない。→ 画面仕様は [04](./04-session-and-integrity.md) §4、
画像の大きさと拡大は §7。

- 実測バイト数（両方）と比率、**PNG / JPEG 両方の実物**（開発者ツールで検証できる）。
- **他のプロファイルならどうなるか**（20 通りの結果。条件で答えが変わることの実演）。
- なぜそうなったかの一行解説（タグから生成 or 手書き）。
- **サイズだけで選ぶな**という注意（劣化・透過・用途。特に JPEG が僅差で勝つケース）。
- 素材の出典とライセンス表記。

## 7. 画像の表示（大きさと拡大ダイアログ）

🔑 **表示の大きさは体験の装飾ではなく、判断材料そのものの問題。**
このクイズは画素の細部（ノイズ・平坦部・輪郭）を読ませる。**縮小するとブラウザが画素を平均化して
ノイズが消える**ので、小さく出すことはプレイヤーから情報を奪うことに等しい。

### 7.1 レイアウト

- **画像だけページ幅の制約（`max-w-3xl`）から外し、ビューポート幅いっぱいに出す。**
  説明文・ボタン・20 プロファイルの表は読み物として 720px のまま保つ。
- 出題画像は**幅いっぱい**。縦は成り行きで、はみ出せばスクロールさせる。
- 🔒 **2 択ボタンは sticky にする。** 画像が縦に長くてもボタンが常に見えることで、
  **「全体を見ないまま答える」流れを作らない**。
  ⚠ iOS Safari のアドレスバー伸縮があるので `dvh` と `env(safe-area-inset-bottom)` を使う。
- 正解画面の PNG / JPEG は**縦積み**で各々を幅いっぱいに出す（横並びは各々が半分になる）。
  バイト数を併記する。ここは [04](./04-session-and-integrity.md) §4 の「検証できる状態」の役。

### 7.2 拡大したときの描画

🔒 **`image-rendering: pixelated` を使う。存在しない画素を作らない。**

- ブラウザ既定の平滑補間は中間画素を発明してノイズをぼかす。**判断材料が実物とずれる。**
- `display` は可逆 WebP なので（[04](./04-session-and-integrity.md) §3.1）、
  `pixelated` で拡大すれば**エンコーダへの入力と 1 画素も違わないもの**を見せられる。
- 倍率は連続でよい（整数倍に縛らない）。非整数倍では 1 画素が n〜n+1 px の
  不均一なブロックになるが、**ブロックの境目は隣接画素の色が違うところにしか現れない**ため、
  平坦な領域に偽のノイズは生じない。

### 7.3 拡大ダイアログ

画像をタップすると全画面のダイアログを開く。

- **全体が収まる倍率（fit）で開く。** 方向感覚を与えてから細部へ向かわせる。
  いきなり 1:1 で開くと、大きい素材では画像の一部しか映らずどこを見ているか分からない。
- 倍率は**ボタン**で切り替える（fit / 1:1 / 2x / 4x）。
  ⚠ **独自のピンチ・パンを実装しない。** パンはネイティブのスクロール、さらなる拡大は
  ブラウザのピンチに任せる。モバイルのピンチズーム許可（[`_grilling/decisions.md`](./_grilling/decisions.md)）と
  二重にならず、キーボードからも操作できる。
- 🔒 **PNG / JPEG の A/B 切替は、正解画面から開いたダイアログにだけ置く。**
  出題中のダイアログに出してはいけない（正解そのもの）。
- A/B 切替では**倍率とスクロール位置を保持する。** 人間の目は「離れた 2 枚の差」より
  「同じ位置での変化」に桁違いに敏感で、位置がずれると切替の意味が失われる。

### 7.4 環境ごとの役割（モバイルファースト）

同じ 2 つのビューが、画面幅によって逆の役目を果たす。**どちらの環境でも「全体」と「細部」の
両方に到達できる**ことが要件で、どちらがどちらを担うかは固定しない。

| | インライン | ダイアログ |
|---|---|---|
| モバイル（幅 390px） | **全体を見る**（1280px 素材で 0.30x・縦は余るのでスクロールなし） | **細部を見る**（1:1 以上・パン） |
| デスクトップ（幅 1400px） | **細部を見る**（1.09〜4.5x・縦スクロール） | **全体を見る** ＋ さらに深く |

- ⚠ **モバイルでは幅いっぱいにしても大きい素材は 0.30x のまま。**
  インラインだけでは細部が見えないので、**ダイアログは必須**であって装飾ではない。

### 7.5 🔒 漏洩の確認

- 拡大で見えるのは**同じ `display` 画像の同じ画素**。新しい情報は増えない。
- 寸法は既に出題レスポンスに含まれ（`questionView.width/height`）、倍率はその導出値。
- 素材のアスペクト比の下限（極端に縦長のものを弾くか）は**未決**。
  UI 側はこれに依存しない（モバイルでは縦が余り、デスクトップは sticky ボタンで成立する）。
  → 素材を増やす段階で判断する（[05](./05-content-pipeline.md) §3.1）。
